# 一、Java / 后端方向

## 1.1 缓存与一致性

### Q：本地缓存（Caffeine）和 Redis 分布式缓存之间的一致性问题怎么解决？

一致性靠两套机制：写入数据时**双写两层缓存**，更新数据时先更新数据库再删除两层缓存。这样下一个查询过来发现缓存是空的，会自己去数据库查最新值，再把它回填到缓存里，相当于让读请求帮我重建缓存。这样比双写更新安全，避免并发下旧值盖新值这个问题。而且Caffeine 本身设了 10 分钟 expireAfterWrite 兜底，如果更新数据时删除两层缓存失败，则脏数据最慢在10分钟后会自动删除。
我这个项目是单机部署redis。因此删自己的 Caffeine 就完事了。那如果上了集群环境下。每台机器的 Caffeine 是各自独立的。不同节点的 Caffeine 不同步问题，我们用 RocketMQ 广播失效消息——更新数据库后发一条 invalidate 消息，所有节点收到后清自己的本地缓存。


### Q：本地缓存怎么实现的？了解底层原理吗？
我用的是 Caffeine。底层基于 **W-TinyLFU 淘汰算法**——比 LRU 多了 LFU 频率统计，用 Count-Min Sketch 估算访问频率，避免突发流量污染缓存。线程安全方面用了类似 ConcurrentHashMap 的分段锁。一个本地缓存应该具有：容量上限、过期策略、并发安全、统计监控（命中率）、淘汰策略。我的配置里开了 `recordStats` 监控命中率。

    第 1 步：引依赖：pom.xml 里加一行caffeine引入caffeine第三方库第 2 步：在CacheConfig.java 里声明一个 一个 Cache<String, Object> 类型的bean，被 Spring 容器托管。）第 3 步：在 CacheClient.java 里注入bean并使用bean
### Q：缓存穿透、缓存击穿、缓存雪崩？

- **穿透**：查询不存在的 key，每次都打到 DB。我项目里用**布隆过滤器**前置拦截非法 ID，加上**空值缓存**双重防护
- **击穿**：热点 key 过期瞬间大量请求打到 DB。我用**逻辑过期**（数据永不过期，过期时异步重建）+ **互斥锁**（mutex）两种策略
- **雪崩**：大量 key 同时过期。我们 TTL 设置时加随机偏移打散过期时间

### Q：只用 Redis 行不行？为什么要用两级缓存？

可以，但高并发下 Redis 网络 IO 是瓶颈。Caffeine 是进程内访问，QPS 能到百万级，比 Redis 高一个数量级。两级缓存的核心价值是**减少 Redis 压力**：热点数据在 Caffeine 直接命中，避免穿透到 Redis。代价是引入了集群一致性问题，如果是多节点的情况下需要配套消息广播失效。

### Q：本地缓存和 Redis 怎么协同工作？什么情况下优先本地？

查询走：**Caffeine（L1）→ Redis（L2）→ DB**这一个路径。每次查询先查 Caffeine（L1），命中直接返回；没命中再去 Redis（L2），命中后回填 Caffeine 让下次查询能本地命中。Caffeine 用于**读多写少的热点数据**（如店铺信息、店铺类型）。**频繁写、强一致**的数据（订单、库存）只走 Redis 不进 Caffeine，避免一致性问题。

### Q：缓存里具体存的什么？

key 用 `cache:shop:{id}` 这种前缀+ID 格式。value 存完整 Shop 对象的 JSON 序列化。逻辑过期场景下 value 是 `RedisData` 包装对象（包含 expireTime + data）。空值场景缓存空字符串，TTL 2 分钟。

### Q：两级缓存下，缓存没删成功 MQ 重试积压崩溃怎么办？

三层防御：
1. **限流**：限制单位时间重试任务数
2. **熔断降级**：检测到 Redis/集群异常，停止重试，直接走 DB（牺牲一致性保可用）
3. **死信队列**：超过最大重试次数（一般 3-5 次）转入 DLQ，人工介入

最关键的是**避免雪崩式重试**——可以用指数退避重试（1s、2s、4s、8s），而不是固定间隔死磕。

### Q：为什么用 Redis？

Redis 内存数据库性能极高，支持丰富数据结构（String/Hash/List/Set/ZSet/GEO/Bitmap），原生支持 Lua 原子操作，社区成熟，适合做缓存、分布式锁、计数器、排行榜、消息队列等多种场景。我项目里用 Redis 做缓存、Token 存储、布隆过滤器、秒杀库存、ZSet 限流、GEO 附近搜索、Bitmap 签到。

### Q：集群环境下不同节点的本地缓存不同步怎么保证一致性？

**RocketMQ 广播消息方案**：更新数据库后，发一条缓存失效消息到广播 Topic，所有节点订阅后清自己的 Caffeine。这是软实时方案。强一致场景直接绕过本地缓存只读 Redis。

### Q：缓存删除失败 MQ 重试最大次数？超过怎么办？

RocketMQ 默认最多重试 16 次（消费失败的话）。我们一般设 3-5 次就够，超过转**死信队列**（DLQ）。DLQ 由独立 consumer 处理：记日志、报警、人工或定时任务最终补偿。

### Q：秒杀 8 点开始，缓存存活时间包含这个时间能解决什么？

提前 N 分钟把秒杀商品库存预热到 Redis，TTL 设到秒杀结束之后，可以**避免冷启动时大量请求打到 DB**（防雪崩、防击穿）。缺点是预热数据如果和实际不一致（如临时调整库存），需要主动刷新。

## 1.2 布隆过滤器

### Q：布隆过滤器用来干啥？底层怎么实现？

**用途**：在缓存层之前过滤"一定不存在"的 key，防缓存穿透。我项目里用 Redisson 的 RBloomFilter，对店铺 ID 和优惠券 ID 做预热过滤。

**底层**：一个大的位数组 + N 个哈希函数。写入时计算 N 个哈希值对应的位置 1。查询时这 N 个位置如果有任何一个是 0，说明一定不存在；如果全是 1，可能存在（假阳性）。

### Q：缺点？支持删除吗？不支持怎么办？

- **不支持删除**（标准 BF）：因为多个元素可能共享某个 bit 位，删除一个会误伤其他元素
- **替代方案**：
  1. **Counting Bloom Filter**：每个 bit 改成计数器，删除时 -1（占用空间增大）
  2. **定期重建**：根据 DB 真实数据全量重新构建 BF
  3. **Cuckoo Filter**：天然支持删除，比 CBF 更省空间

### Q：缺点是假阳性还是假阴性？

**假阳性**（False Positive）：可能误判"存在"，但绝不会误判"不存在"。原因：哈希冲突导致多个元素的 bit 位重叠，一个不存在的 key 可能恰好哈希到全是 1 的位置。

### Q：秒杀场景用 BF 除了假阳性还有啥缺点？

- **写入开销**：高并发写入 BF（如新商品上架）可能成为瓶颈
- **容量预估难**：BF 大小要预设，超过后假阳性率飙升
- **不支持热数据淘汰**：BF 装满了只能重建
- **分布式 BF 同步成本高**：多节点 BF 需要同步状态

### Q：用过 Counting Bloom Filter 吗？

了解原理但项目没用，因为项目场景是**店铺信息很少删除**，标准 BF 已够用。CBF 把每个 bit 扩成 4-bit 计数器，写入 +1 删除 -1。代价是空间 4 倍，读写 CAS 复杂。

### Q：要更新商户信息，BF 怎么更新？

商户信息**修改**不影响 BF（key 还在）。**新增商户**直接 `bloomFilter.add(id)`。**删除商户**用以下方案：
1. 如果用 CBF，直接 `delete()`
2. 如果用标准 BF，**定期全量重建**（凌晨低峰）
3. 项目里 shop 删除是软删，BF 不需要变，下游业务逻辑判断 status

## 1.3 秒杀

### Q：一人一单和秒杀怎么实现？库存超卖怎么解决？

**完整流程**：
1. **Lua 脚本原子操作**（seckill.lua）：判断库存 + 判断是否已购 + 扣减库存 + 记录订单 SET，**全在 Redis 内单线程执行**，杜绝超卖
2. **库存判断**：`if stock <= 0 return 1`（库存不足）
3. **一人一单**：`if SISMEMBER orders:{voucherId} userId == 1 return 2`（重复购买）
4. 通过 Lua 校验后，发**RocketMQ 消息**异步下单
5. 消费者用 **Redisson 分布式锁**（key 为 userId）做兜底，防止 MQ 重复消费导致一人多单
6. DB 层**乐观锁**：`UPDATE seckill_voucher SET stock=stock-1 WHERE voucher_id=? AND stock>0`

### Q：库存扣减用什么实现？Lua 脚本怎么写的？

```lua
-- KEYS[1]=stock key, KEYS[2]=order set key
-- ARGV[1]=voucherId, ARGV[2]=userId, ARGV[3]=orderId
local stockKey = KEYS[1]
local orderKey = KEYS[2]

-- 1. 库存检查
if (tonumber(redis.call('get', stockKey)) <= 0) then
    return 1  -- 库存不足
end
-- 2. 一人一单检查
if (redis.call('sismember', orderKey, ARGV[2]) == 1) then
    return 2  -- 重复下单
end
-- 3. 扣减库存 + 记录用户
redis.call('incrby', stockKey, -1)
redis.call('sadd', orderKey, ARGV[2])
-- 4. 发送消息（如果用 Redis Streams）
return 0  -- 成功
```

### Q：怎么防止程序恶意刷优惠券？

我项目里有**自研 ZSet 滑动窗口限流**（`@SlidingWindowLimit` AOP 注解），秒杀接口设了 **20 req/min/user**。还有几层：
1. **登录拦截器**：必须登录，token 验证
2. **一人一单**：Redis SET 校验
3. **图形验证码**（生产环境）
4. **风控**：IP 频率检测、设备指纹

### Q：单实例下 Lua 能保证原子性，集群多 key 操作有什么问题？

Redis Cluster 用**槽位（slot）分片**，不同 key 可能在不同节点。**Lua 脚本必须所有 key 在同一节点**才能执行，否则报错 `CROSSSLOT`。解决方案：
1. **Hash Tag**：用 `{userId}` 强制相同前缀的 key 落同一槽位
2. **业务拆分**：避免跨 key 原子操作
3. **改用分布式事务**（如 Redisson 的 RTransaction）

### Q：秒杀结束后 Redis 库存同步回 MySQL 部分失败怎么办？

我项目里**库存扣减实时同步 DB**（消费者每收到 MQ 消息就 update DB），不是结束后批量同步。如果是批量同步场景：
1. **重试 + DLQ**：失败的记录进死信队列
2. **对账任务**：定时扫描 Redis 与 MySQL 差异，补偿
3. **延迟消息兜底**：用 RocketMQ 延迟消息，X 分钟后再核对一次

### Q：Redis 主从有什么问题？

**项目用的是单机 Redis，主从是八股回答**：
1. **主从延迟**：异步复制可能丢数据
2. **脑裂**：主从切换时双主写入
3. **故障切换数据丢失**：主挂了未同步的数据丢失
4. **解决方案**：哨兵集群、`min-slaves-to-write` 参数、Redis 6+ 的多线程复制

### Q：流量增加 100 倍架构怎么重构？

1. **接入层**：Nginx 负载均衡 + 限流
2. **缓存层**：升级为 Redis 集群，多副本，加 Caffeine L1
3. **MQ**：RocketMQ 集群多 broker，提升吞吐
4. **数据库**：主从读写分离 + 分库分表
5. **服务**：横向扩容 + K8s 自动扩缩容
6. **监控**：Prometheus + Grafana 全链路压测
7. **降级方案**：核心接口预案、非核心服务降级
8. **CDN**：静态资源前置

## 1.4 消息队列

### Q：RocketMQ 延迟消息怎么用？

我项目里订单创建后会发**延迟消息**到 `order-timeout` Topic，延迟 15 分钟。15 分钟后消费者收到消息，检查订单是否已支付：未支付则关闭订单 + 释放库存。RocketMQ 的延迟级别有 18 个固定档位（1s/5s/10s/.../2h），项目里选 5（1m）或 16（30m）。生产代码：`message.setDelayTimeLevel(16)`。

### Q：为什么选 RocketMQ？

1. **延迟消息原生支持**（Kafka 不支持，RabbitMQ 要装插件）
2. **顺序消息**支持
3. **事务消息**支持（解决 MQ 与 DB 一致性）
4. **阿里背书** + 国内文档全
5. **单机吞吐 10 万级**够用，不需要 Kafka 那种百万级吞吐

### Q：消息生产消费流程？怎么保证不丢失/不重复？

**不丢失三处保障**：
- **生产端**：同步发送 + 失败重试，开启事务消息
- **Broker**：同步刷盘 + 主从同步
- **消费端**：手动 ACK，处理成功后再确认

**不重复消费**：
- **业务幂等**：用 orderId 做唯一索引，重复消费 DB 拒绝
- **去重表**：消费前先查 `consumed_messages` 表

### Q：Redis 实现消息队列？和主流 MQ 的不足？

Redis 实现 MQ 有 3 种：
1. **List 的 LPUSH/BRPOP**（简单队列）
2. **Pub/Sub**（不可靠，订阅者不在线消息丢失）
3. **Streams**（5.0+，类似 Kafka 但功能弱）

**不足**：
- 持久化弱（Redis 主要内存，宕机风险）
- 无完善死信队列
- 无延迟消息（要自己用 ZSet 模拟）
- 无事务消息
- 集群模式下消费者负载均衡复杂

### Q：削峰解耦后吞吐量提升多少？

项目没做严谨压测，话术：
> 引入 RocketMQ 异步下单后，秒杀接口响应时间从同步处理的 ~200ms 降到 ~30ms（只做 Lua 校验和发消息），TPS 从约 500 提升到约 3000+。具体数据需要在生产环境压测验证。

## 1.5 Redis 集群与分布式锁

### Q：Redis 集群有哪几种方式？

**项目用单机，集群是八股**：
1. **主从复制**：一主多从，读写分离
2. **哨兵模式（Sentinel）**：哨兵监控主从，自动故障转移
3. **Cluster 集群**：去中心化，16384 槽位分片，原生支持

### Q：主观下线和客观下线？

- **主观下线（SDOWN）**：单个哨兵 ping 主节点超时（`down-after-milliseconds`）
- **客观下线（ODOWN）**：超过 `quorum` 数量的哨兵都认为主下线了，正式标记下线，触发故障转移

### Q：哨兵选主流程？

1. **选举领导哨兵**（Raft 算法）：先发现客观下线的哨兵发起投票，多数派当选 Leader
2. **Leader 选新主节点**规则：
   - 过滤掉下线/不健康从节点
   - 优先级（`slave-priority`）高的优先
   - 复制偏移量（offset）最大的优先（数据最新）
   - runId 最小的优先（启动早的）

### Q：Redisson 分布式锁怎么用？底层？

**用法**：
```java
RLock lock = redissonClient.getLock("lock:order:" + userId);
try {
    boolean locked = lock.tryLock(2, 10, TimeUnit.SECONDS);
    if (locked) {
        // 业务
    }
} finally {
    lock.unlock();
}
```

**底层**：
- 基于 Redis 的 SETNX + Lua 实现
- 锁结构是 Hash：`{lockKey: {threadId: reentrantCount}}`
- 支持**可重入**（同线程多次加锁）
- 释放时校验 threadId（Lua 原子操作）

### Q：看门狗机制？

Redisson 默认 30 秒锁过期。线程加锁成功后，启动**WatchDog**（守护线程），每 **10 秒**（即 lockExpireTime / 3）检查一次，如果业务还在执行，自动续期到 30 秒，防止业务未完成锁就释放了。**只有不指定 leaseTime 时才有看门狗**，`tryLock(waitTime, leaseTime, unit)` 显式传 leaseTime 时不启用。

## 1.6 基础八股

### Q：ThreadLocal 存了什么？有什么问题？底层？

**项目里 `UserHolder` 用 ThreadLocal 存登录用户 UserDTO**，配合 `RefreshTokenInterceptor` 在请求开始时塞入，请求结束 `removeUser()` 清理。

**底层**：每个 Thread 内部有 ThreadLocalMap，key 是 ThreadLocal 实例（**WeakReference**），value 是用户对象。

**问题**：
- **内存泄漏**：key 是弱引用，GC 后变 null，但 value 还在 Map 里。线程池场景下线程不销毁，value 累积。
- **解决**：用完一定要 `remove()`

### Q：为什么 GC 不能回收 value？怎么办？

Map 的 entry 持有 value 的强引用。即使 key 被 GC（弱引用），entry 本身还在 Map 中，value 不会被回收。**线程池中线程长期存活**，问题更严重。

**解决**：
1. **使用 try-finally 强制 remove**
2. ThreadLocal 内部的 `get/set/remove` 会顺便清理 key 为 null 的 stale entry

### Q：附近店铺怎么实现？

用 Redis 的 **GEO 数据结构**。每个店铺以 (经度,纬度,shopId) 形式存入：`GEOADD shop:geo:{typeId} 经度 纬度 shopId`。查询时用 `GEOSEARCH FROMLONLAT 用户经纬度 BYRADIUS 5000 m WITHDIST ASC` 获取附近店铺并按距离排序，分页返回。

### Q：主键怎么做？

用**自研 Snowflake 雪花算法**（`RedisIdWorker`）：64 位 long，符号位 1bit + 时间戳 31bit（秒级，2022-01-01 起）+ 序列号 32bit（Redis INCR 当日 key）。优点：趋势递增、全局唯一、不依赖 DB。

### Q：项目最大技术挑战？

**AI Agent 的工具调用循环设计**：
- LLM 输出格式不稳定，需要解析工具调用结果回灌
- 循环终止条件设计（max-steps=20 防死循环 + LLM 主动调 terminate）
- 异常处理（工具失败要不要重试、要不要中断）
- token 控制（滑动窗口截断历史消息）
- SSE 流式输出与异步执行的协调

最终用 ReAct 模式 + 观察者模式（AgentLoopObserver）+ 事件驱动（ChatMessageCreatedEvent 异步触发）解决。

# 二、AI / Agent 方向

## 2.1 RAG 基础

### Q：项目使用的 RAG 技术？

我用的是 **Spring AI + Milvus** 实现的 RAG，Embedding 用 **bge-m3（1024 维）**。三个独立向量索引：
1. **knowledge_vector**：平台规则知识库
2. **shop_profile_vector**：店铺画像
3. **blog_review_vector**：用户评论

**检索策略迭代过三个阶段**（项目里完整跑通并量化对比）：
- **阶段一 vector**：基础向量 Top-K + 关键词 Fallback + Metadata 过滤（按 shopId / city / category 限定范围）
- **阶段二 hybrid**（Plan E）：加 **Lucene BM25 + RRF k=60** 跟向量召回合并，修复了"杭州的中餐推荐"这种宽泛 query 向量召回弱的问题——review collection 整体 relevancy 从 0.05 → 0.71
- **阶段三 hybrid+rerank**（Plan G）：召回 top-20 后加 **BAAI/bge-reranker-v2-m3 cross-encoder 精排**取 top-5（走 SiliconFlow `/v1/rerank`，失败降级回 RRF 原序）——shop_profile 从 0.32 → 0.38，整体 relevancy 从 0.59 → 0.67

**业务侧 `BusinessRagRouter` 三档路由**（默认走最强档 `hybrid+rerank`），实现**链式自动降级**：rerank 调用失败 → 降级 hybrid；hybrid 异常 → 降级 vector。`/actuator/rerank-stats` 暴露调用次数 / 失败次数 / 平均延迟，生产环境可监控。

**整体 relevancy 从 0.305 → 0.670（+36%）**，结果在 200 query 评估集上独立验证过（Plan H）。

### Q：RAG 全流程？

1. **数据预处理**：文档切片（chunk）→ Embedding 模型向量化 → 存入 Milvus（带 metadata）
2. **检索阶段**：用户 query → Embedding → 向量相似度搜索 Top-K → 取出文本片段
3. **生成阶段**：检索片段 + query 拼入 Prompt → LLM 生成 → 流式返回

### Q：RAG 召回效果怎么评估？怎么优化？

**评估维度**：
- 召回率（Recall@K）：相关文档在 Top-K 中的比例
- 准确率（Precision）
- MRR（Mean Reciprocal Rank）
- 答案质量人工打分

**优化方法**：
- **查询重写**（Query Rewriting）：LLM 改写口语化问题
- **混合检索**：向量 + BM25
- **重排序**（Reranking）：Top-K 后用 Cross-Encoder 精排
- **元数据过滤**：缩小检索范围
- **chunk 大小调优**

### Q：RAG 上传的什么文档？

我项目里 RAG 索引的不是上传文档，是**数据库内已有的业务数据**：
- 知识库索引：平台规则文本
- 店铺画像索引：店铺名、地址、营业时间、特色菜等结构化字段拼接
- 评论索引：博客评论文本

通过 `/index/rebuild/all` 或 `/index/rebuild/shop/{id}` 接口重建索引。

### Q：RAG 流程是别人封装的吧，你自己实现了什么？

Spring AI 提供了 VectorStore、ChatClient 等基础抽象，但 RAG 编排逻辑是我自己写的：
1. **AiRagRetriever**：自定义混合检索策略（向量 + 关键词兜底 + Metadata 过滤）
2. **三级索引设计**：根据查询意图路由到不同 collection
3. **召回结果与 Prompt 拼接的格式**
4. **Agent 循环中将 RAG 检索作为一个工具暴露**

不是直接调 `RetrievalAugmentationAdvisor` 那种黑盒。

### Q：为什么用 Spring AI？

1. **Spring 生态无缝**：项目本来就是 Spring Boot 3.x
2. **OpenAI 兼容协议**：换模型只改配置（我们对接的阿里云千问也是 OpenAI 兼容）
3. **VectorStore 抽象**：换向量库（Milvus、Chroma、PGVector）零成本
4. **MCP 客户端原生支持**

LangChain4j 也用过 demo，但生态没 Spring AI 整合度高。

### Q：RAG 文档更新了怎么办？能同步更新吗？

项目暴露了 `/index/rebuild/shop/{shopId}` 接口，**单店铺触发增量重建**。完整方案：
1. **手动触发**：管理员调接口
2. **DB 变更触发**：店铺信息更新时发事件，监听器异步重建该店向量
3. **定时任务**：凌晨低峰全量重建（兜底）

## 2.2 对话记忆与上下文管理

### Q：多轮对话记忆方案？

我用的是**滑动窗口法**：通过 `ai.agent.memory.window-size: 8` 配置只保留最近 8 条消息。每次发起 LLM 调用前，从 DB 加载会话最近 N 条 message，跳过 tool 消息只保留 user/assistant，拼成上下文。

未来计划加**异步摘要**：窗口满时把更早的消息让 LLM 总结成 1-2 句话，既保留语义又控制 token。

### Q：压缩上下文丢失手机号、地址怎么办？

**关键字段抽取存储**：在压缩前用 LLM 或正则提取实体（手机号、地址、订单号），单独存到一个 KV 结构（`session:entities:{convId}`）。每轮对话都把这些"硬信息"原样拼回 Prompt，不让它们被压缩掉。

### Q：用户提示词指代不明怎么办？

**指代消解（Coreference Resolution）**：
1. **改写式**：LLM 把"它"替换成具体实体，用最近 K 轮上下文做改写后再检索
2. **澄清反问**：识别到模糊指代时反问"您说的是 X 还是 Y？"
3. **基于历史的实体追踪**：维护 session 内的实体列表，按时间近因匹配

### Q：上下文记忆管理做了哪些优化？

1. **滑动窗口截断**（已实现）
2. **跳过 tool 消息**只留 user/assistant 节省 token
3. **会话隔离**：每个 conversationId 独立窗口
4. **未实现的优化方向**：异步摘要、关键字段单独存储、向量化历史检索（长期记忆）

## 2.3 Prompt 与系统优化

### Q：最终给大模型的 Prompt 怎么构建的？

分三层：
1. **System Prompt**：角色定义（"你是本地生活推荐助手"）+ 工具列表 + 输出格式约束
2. **Context**：RAG 检索结果（店铺信息、评论片段）
3. **History**：滑动窗口的历史 user/assistant 消息
4. **Current Query**：本轮用户输入

ReAct 模式还会把 Tool Call 结果作为 `tool` 角色消息回灌。

### Q：问答系统优化方向？

- **查询重写**：提升 RAG 召回准确率
- **异步摘要**：解决长对话 token 问题
- **重排序**：Top-K 后加 Reranker 精排
- **缓存**：常见 query 的 LLM 回答做语义缓存
- **Multi-Agent**：复杂任务拆给专责子 Agent
- **微调**：领域 SFT 提升专业问答质量

## 2.4 流式输出与延迟优化

### Q：怎么用流传递到前端？

我用的是 **SSE（Server-Sent Events）**，不是 ResponseBodyEmitter（Spring MVC 的同类技术）。

接口：`GET /ai/agent/conversations/{id}/stream`，返回 `text/event-stream`。后端拿到 LLM 流式 chunk 后转 SSE event 推给前端。事件类型有：
- `status`：思考中
- `answer_delta`：逐 token 推送
- `answer_done`：完整回复
- `message`：完整 message 对象（含 messageId）

前端用 `EventSource` API 监听。

### Q：大模型部署在海外延迟大怎么办？

1. **就近部署**：用国内可访问的 endpoint（如阿里云 DashScope，我项目就是这样）
2. **请求合并**：减少调用次数
3. **流式输出**：用户可以一边看一边等，体感延迟降低
4. **预生成/缓存**：常见问题预先生成
5. **Edge 加速**：CDN/边缘节点
6. **降级**：超时返回模板回复或快速模型

### Q：大模型超时或不可用怎么处理？

我项目里 `AiAgentProperties` 设了四级超时：
```yaml
connect-timeout-seconds: 10
read-timeout-seconds: 90
write-timeout-seconds: 90
call-timeout-seconds: 120
```

超时/异常时：
1. **降级**：返回模板回复（"AI 助手繁忙，请稍后再试"）或快速模型
2. **熔断**：连续失败 N 次熔断 5 分钟（可加 Resilience4j）
3. **异步通知**：用户先收到"正在处理"，结果异步推送
4. **日志报警**：监控失败率

## 2.6 Agent 工具调用与 MCP

### Q：Agent 怎么调用外部工具？

**ReAct 循环步骤**：
1. **工具注册**：在 `DianPingAgentTools` 类中用 `@Tool` 注解定义工具，Spring AI 自动生成 OpenAI Function Schema
2. **LLM 决策**：把工具列表注入 Prompt，LLM 输出 `tool_calls` JSON（工具名 + 参数）
3. **本地执行**：解析 JSON，反射调用对应方法
4. **结果回灌**：执行结果作为 `tool` 角色消息加入 messages，再调一次 LLM
5. **循环直到 LLM 调用 `terminate` 工具**输出最终答案，或达 max-steps（20）强制结束

### Q：Agent 怎么管理 Skill？

**框架控制**：所有工具在 `DianPingAgentTools`、`McpLocalLifeTools`、`AgentLoopControlTools` 中静态注册，Spring 启动时通过 `@Tool` 注解扫描收集，统一暴露给 LLM。Skill 自身不参与加载控制。

好处是**集中管理**、易于审计权限。坏处是不能动态加载（要重启）。

### Q：Agent 项目用了现成框架吗？

**用了 Spring AI 做 LLM 调用层**（ChatClient、VectorStore、Tool 注解），但**Agent 循环逻辑全是自己手写**：
- `AgentLoopExecutor`：循环控制
- `ManualToolAgentLoopExecutor`：工具调用编排
- `AgentLoopObserver`：观察者模式上报状态
- 没用 LangGraph、AutoGen 这类完整 Agent 框架

### Q：MCP 工具怎么处理？MCP 网关讲讲？

**MCP（Model Context Protocol）** 是 Anthropic 提出的 LLM 工具调用标准协议。我项目里 `McpLocalLifeTools` 暴露两个工具：
- `getRouteAdvice`：路线规划
- `getWeatherDiningAdvice`：天气餐饮建议

通过 HTTP 调远程 MCP server，配置在 `ai.agent.mcp.*`。带超时和兜底（MCP 失败用本地默认逻辑）。

**MCP 网关概念**：统一接入多个 MCP server，做鉴权、限流、协议转换、监控。我项目目前是直连，没做网关层。

### Q：MCP server 怎么保证消息不丢失/不重复投递？

我**在 MCP server 层加了 RocketMQ**作为消息缓冲：
- **不丢失**：Producer 同步发送 + Broker 同步刷盘 + Consumer 手动 ACK
- **不重复**：每个 MCP 请求有 traceId 作为幂等键，server 维护去重表
- **重试**：失败重试 3 次进 DLQ

## 2.7 Bad case 与幻觉

### Q：Badcase 怎么处理？幻觉怎么应对？

**幻觉应对**：
1. **RAG 兜底**：只允许 LLM 基于检索到的真实数据回答（Prompt 里强制"未检索到相关信息时回答'暂无数据'"）
2. **置信度判定**：检索相似度低于阈值（`similarity-threshold: 0.65`）时拒答
3. **结构化输出**：要求 LLM 输出 JSON，无法填充字段时明确返回 null
4. **后处理校验**：返回的店铺名/ID 必须在 DB 中存在，否则丢弃
5. **Bad case 收集**：用户点踩按钮，记录到 DB 用于后续优化

### Q：让模型判断能否回答这个问题？

在 System Prompt 里加规则：
> 如果检索到的内容无法支撑回答用户问题，请回复"该问题超出我的知识范围，建议联系人工客服"，不要编造。
