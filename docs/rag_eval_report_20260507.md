## 1.5 评估方法的边界条件声明

> 本次报告同时呈现两套评估方法的指标：**ID-比对 baseline** + **LLM-as-judge (reference-free)**。
> 两个方法不是替代关系，而是**互补**——各能给什么、不能给什么如下，由读者自行判断。

| 维度 | baseline (ID-比对) | LLM-as-judge (reference-free) |
|---|---|---|
| Recall@K | ✅ 可算 | ❌ **天然没有**——reference-free 范式没有 ground truth 全集做分母 |
| Precision@K | ✅ 可算，但准确性依赖 ground truth 标注质量 | ✅ 可算，由 LLM 判 (query, doc) 二元相关性 |
| MRR | ✅ 可算 | ✅ 可算（按 LLM 判相关的最高排名） |
| HitRate | ✅ 可算 | ✅ 可算 |
| 评估成本 | 低（一次性） | 中（每条 query × top-K 都需要 LLM 调用）|
| 评估集设计敏感度 | **高**——ground truth 选择直接决定数字含金量 | 低——只看 (query, doc) 对，不依赖标注 |

**本次特别说明**：baseline 的 shop / review 类用"评论数 top5"作为 ground truth，与向量检索的"语义相似度"是两个维度，导致 Recall/Precision 数字偏低。这是评估集设计错配，不是 RAG 检索本身的问题。详见 [Section 6.5 评估集设计反思](#65-评估集设计反思--llm-as-judge-验证结果)。

> 方法论参考 [Ragas 论文](https://arxiv.org/abs/2309.15217) 关于 reference-based vs reference-free trade-off 的讨论。

### 5.7.5 观察分析

分层评估框架下，将 retrieval 指标 + generation 指标交叉，可以定位失败根因：

| 模式 | retrieval | generation | 含义 |
|---|---|---|---|
| 健康 | 高 | 高 | 召回好 + 模型用得好 |
| 模型幻觉 | 高 | 低 | 召回正确但模型脱离 contexts 编造 → 调 generation prompt / 升级模型 |
| 召回不足 | 低 | 高 | 召回少但模型靠常识答（不算 RAG 闭环）→ 提升 retrieval 召回率 |
| 双低 | 低 | 低 | query 难度大或 ground truth 缺失 → 评估集设计问题 |

## 6.5 评估集设计反思 + LLM-as-judge 验证结果

### 反思：baseline 数字偏低的真实原因

Plan B baseline 跑完后，shop / review 的 Recall ≈ 0、knowledge Recall = 0.70。
**初看像是 RAG 检索能力差，但 failure case 逐条排查后发现：召回的店铺业务上完全合理（同城同品类、招牌菜匹配 query 关键词），只是不在 ground truth 标注的那 5 个 shop_id 里。**

根因定位到**评估集设计错配**：

- shop / review 类的 `relevant_ids` 用"评论数 top5"作为 ground truth
- 但向量检索靠**语义相似度**——"用户 query 和 shop 描述的语义匹配度"
- "评论数热度"和"语义相关"是**两个维度**，强行用前者作为后者的标注，必然出现：召回的店在业务上对，但被判 miss

knowledge 类不受影响是因为 question → answer 是一对一映射，ID 比对刚好对齐了语义匹配。

### LLM-as-judge 验证：换评估方法不换 ground truth

Plan C 没有重生成 `eval_queries.jsonl`（那本质上仍是 ID 比对范式），而是引入 **Reference-free LLM-as-judge**：
评估时跑 RAG 检索，对每个 retrieved doc 让 LLM (Claude Haiku 4.5) 二元判断"是否与 query 相关"，直接计算 Precision@K + LLM-judged HitRate。

**这是 [Ragas](https://github.com/explodinggradients/ragas) 推荐的标准做法**：当 ground truth 难以获得或标注质量存疑时，用强 LLM 当 judge 给出 reference-free 评估，绕开"必须命中那几个特定 ID"的硬要求，更符合 RAG 真实评估目标。

### 结论

- **如果 LLM-judge Precision 显著高于 baseline Precision**：证明 RAG 召回的文档在语义上是相关的，baseline 数字偏低是**评估集设计问题**，不是检索能力问题
- **业务最优阈值**：shop / review 的最优阈值要等到评估集修对（或长期用 LLM-judge）后才能确定。在那之前，`ai.agent.rag.similarity-threshold: 0.65` 是基于 Plan B baseline 配的保守值，**评估集修对前不动**
- **下一步可选**：(a) 用 LLM-as-judge 重标 ground truth 生成 v2 评估集；(b) 引入 rerank 看 LLM-judge Precision 能否再提升 10%

本评估框架的设计思路对照以下业界标杆开源项目（**只参考思想，不引入依赖**）：

- [Ragas](https://github.com/explodinggradients/ragas) — 两层评估框架 + 指标命名（context_recall / context_precision）
- [LlamaIndex](https://github.com/run-llama/llama_index) — RetrieverEvaluator 抽象、三阶段解耦（测试集 / 执行 / 报告）
- [LangChain](https://github.com/langchain-ai/langchain) — trace 思路应用于 failure case 分析
- [Milvus](https://github.com/milvus-io/milvus) — metadata filtering 一等公民的工程实践

具体实现是 Java + Spring AI + Milvus（业务栈），核心评估逻辑约 50 行 Java（标准 IR 公式：Recall@K / Precision@K / MRR）。
