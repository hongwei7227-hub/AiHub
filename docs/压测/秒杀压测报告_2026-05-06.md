### 1.3 业务链路（[VoucherOrderServiceImpl.java](../../src/main/java/com/cityaihub/service/impl/VoucherOrderServiceImpl.java#L93)）
```
HTTP POST /voucher-order/seckill/{id}
   ↓ Tomcat 工作线程
   ↓ 拦截器：authorization header → Redis login:token:{uuid} → UserHolder
   ↓ Lua 原子脚本 seckill.lua：库存检查 + 一人一单检查 + INCRBY -1 + SADD userId
   ↓ 0=成功 → markOrderPending(orderId) → RocketMQTemplate.syncSend("seckill-order-topic", orderJson)
   ↓ 返回 Result.ok(orderId)（用户 1ms 内拿到结果）
   ↓
   ↓ [异步] @RocketMQMessageListener consumer：拿分布式锁 lock:order:{userId}
   ↓ INSERT tb_voucher_order
   ↓ UPDATE tb_seckill_voucher SET stock=stock-1 WHERE voucher_id=? AND stock>0
   ↓ DEL seckill:order:pending:{orderId}
```

### 1.4 Lua 脚本返回码（[seckill.lua](../../src/main/resources/seckill.lua)）
| 返回 | 含义 |
|---|---|
| 0 | 抢单成功 |
| 1 | 库存不足 |
| 2 | 重复下单 |
| 3 | Redis 库存未预热 |

## 二、压测设计

### 2.1 关键参数
| 参数 | 值 | 说明 |
|---|---|---|
| `CONCURRENT_REQUESTS` | 500 | 总请求数（库存的 2.5 倍）|
| `THREAD_POOL_SIZE` | 50 | 物理并发线程 |
| `STOCK` | 200 | 测试券初始库存 |
| `TOKEN_COUNT` | 1000 | 预生成的用户 token 数 |
| `MQ_CONSUMER_WAIT_SECONDS` | 30 | 等 MQ 消费完成最大窗口 |
| 同步起跑机制 | `CountDownLatch start` | 所有 worker 阻塞在 await，主线程一次 countDown |

为什么选这些数：
- **500 vs 库存 200**：制造 2.5 倍的请求数过载，确保有足够多请求会被 Lua 脚本以"库存不足"打回，验证 lua 原子性在并发下不超卖。
- **50 物理线程**：本地 8 核机器跑 50 线程足够压出竞争；线程多了反而被 CPU 调度抖动模糊掉真实延迟。
- **1000 token 预生成**：500 并发 / 同 voucher 必然要 500 个不同 user，token 给到 1000 留一倍冗余，且批量 seed 一次成本不高。
- **30s MQ 消费窗口**：实际消费完只用了 23 秒（200 条订单走 20 个消费线程），30s 是上限。

### 2.2 三个测试类的分工
| 类 | 职责 |
|---|---|
| [SeckillTestSeed.java](../../src/test/java/com/cityaihub/seckill/SeckillTestSeed.java) `createSeckillVoucher()` | 调 `voucherService.addSeckillVoucher()` 造一张 stock=200 秒杀券；voucherId 写到 `target/test-classes/seckill-voucher-id.txt`；自动写 Redis `seckill:stock:{id}=200` 预热 |

### 3.2 RocketMQ broker IP 修复（关键坑）

**症状**：第一次跑 storm 全部 500 个请求 fail，错误 `RemotingSendRequestException: send request to /172.17.0.2:10911 failed`，broker 端日志为空。

**排查**：
- 容器 `docker exec rmqbroker ps -ef` → broker JVM 活着
- nameserver 注册的 broker addr = `172.17.0.2:10911`（docker bridge 内部 IP）
- 从 Windows host 用 `Test-NetConnection / TcpClient` TCP 测连显示 `connected_in=9ms`，但 `stream.Write(8 bytes)` 后 broker 完全收不到、不返回任何响应

**根因**：Docker Desktop on Windows 的 vpnkit 让 Windows host 看似能 connect 到 docker bridge 内部 IP，但实际数据不路由到容器进程。RocketMQ 客户端拿到 nameserver 返回的 `172.17.0.2` 后用真实 IP 连接，长连接握手失败。

**修复**：让 broker 通过 broker.conf 自报 `host.docker.internal`（Docker Desktop 在 Windows host 上也注册此名解析为 host 自身），加上 broker 端口已 port-mapping 到 host:10911，于是客户端经过 `host.docker.internal:10911 → host:10911 → 容器 10911` 走通 port forwarding。

具体操作：
```powershell
# 1. 在 host 准备 broker.conf
$conf = "C:\Users\MSI\AppData\Local\Temp\rmq-conf"
New-Item -ItemType Directory -Path $conf -Force | Out-Null
$lines = @(
  'brokerClusterName = DefaultCluster',
  'brokerName = broker-a',
  'brokerId = 0',
  'deleteWhen = 04',
  'fileReservedTime = 48',
  'brokerRole = ASYNC_MASTER',
  'flushDiskType = ASYNC_FLUSH',
  'brokerIP1 = host.docker.internal'
)
$lines | Set-Content -Path "$conf\broker.conf" -Encoding ascii

# 2. 重建 broker 容器，挂载 conf 并指定 -c
docker rm -f rmqbroker
docker run -d --name rmqbroker `
  -p 10909:10909 -p 10911:10911 `
  -e NAMESRV_ADDR=host.docker.internal:9876 `
  -e JAVA_OPT_EXT='-Xms256m -Xmx512m' `
  -v "${conf}\broker.conf:/etc/rocketmq/broker.conf:ro" `
  apache/rocketmq:5.1.0 `
  sh mqbroker -c /etc/rocketmq/broker.conf
```

修复后 nameserver 注册的 addr 变为 `host.docker.internal:10911`，storm 一次跑通。

## 六、结论与简历用 narrative

### 6.1 业务结论
- Lua 脚本在 500 并发下原子性可靠：扣库存 + 一人一单两条 redis.call 在脚本内串行，没出现一票超卖或重单。
- RocketMQ 解耦让用户路径轻量化：HTTP P50 只有 13ms（核心路径只有 Lua + Redis，落库走异步），同时保留消费幂等（基于分布式锁 `lock:order:{userId}`），消费失败不丢单。
- Redis stock 与 DB stock 终态一致，pending key 全清，验证了 reserve→commit→clear 三步保护机制完整。

### 6.2 简历可用一句话
> 自建 Java 并发压测套件（500 用户 50 物理线程 CountDownLatch 同步起跑），抢同一张库存 200 秒杀券。
> 实测：**0 超卖，0 重单，910 req/s 吞吐，P50 13ms / P95 379ms**；MQ 异步落库 23s 内全 drain。
> 验证了 Redis Lua 原子扣库存（一人一单 + 库存判断）+ RocketMQ 异步消费幂等 + Redis 分布式锁的核心链路。

### 6.3 排坑亮点（面试故事点）
> 第一轮 storm 全部失败 — 9 秒 RocketMQ syncSend 超时。排查：broker 自报 docker bridge 内部 IP 172.17.0.2 给 nameserver；Windows host 上 PowerShell `TcpClient.Connect` 显示握手成功但 `Write` 8 字节后 broker 完全无响应——Docker Desktop on Windows 的 vpnkit 让 TCP 看似可达但数据不通。修复：broker.conf 设 `brokerIP1=host.docker.internal`，重建容器，让客户端走 port-mapping `host:10911 → 容器:10911`。第二轮 0.5 秒跑完。
